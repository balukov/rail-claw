# OpenClaw 2026.5.27 → 2026.9.2 upgrade

**Date:** 2026-09-06
**Status:** Approved, pending implementation
**SnapClaw release:** 0.10.0

## Problem

SnapClaw pins `ghcr.io/openclaw/openclaw:2026.5.27`. Twelve stable OpenClaw releases have
shipped since (6.9 … 9.2). Bumping the pin alone breaks every existing deployment and every
fresh install. Everything below was verified against the real `2026.9.2` image and CLI, and
by rehearsing the upgrade three times on a genuine 5.27 state directory — not from release
notes alone.

What breaks with a bare pin bump:

| Change in OpenClaw | Effect on SnapClaw today |
| --- | --- |
| Base image is Node 24 (was 22) | `node-pty` is compiled in a `node:22` builder stage → ABI mismatch, terminal dead |
| State migrations (config, plugins, sessions, device identity → SQLite) are owned by `doctor --fix`; the Gateway refuses to start on legacy state | Gateway exits 1 on first boot **and on every restart after** (`Legacy workspace setup state requires migration … run openclaw doctor --fix`). The crash watchdog turns this into an endless restart loop — the bot is down for all 16 live installs |
| Provider `openai-codex` is gone; ChatGPT OAuth lives under provider `openai` | First-time onboarding (`--auth-choice openai-codex`) and re-auth (`--provider openai-codex`) both fail |
| Auth profiles moved out of `openclaw.json` into SQLite | Status panel reads `auth.profiles` → "Codex connected" is permanently false |
| `gateway.controlUi.allowInsecureAuth` removed from the (strict) schema | `ensureConfig()` re-adds it every boot → `openclaw.json` is invalid on every boot; `config validate` fails, `plugins install` refuses to run |
| `gateway.controlUi.dangerouslyDisableDeviceAuth` retired and ignored | Control UI browsers must device-pair; today's proxy flow has no way to approve them |
| `channels.telegram.pollingStallThresholdMs` retired (strict schema) | Setting `OPENCLAW_TELEGRAM_POLL_STALL_MS` invalidates the config |
| `config set channels.telegram.botToken` no longer enables the Telegram plugin | New installs depend on an undocumented runtime auto-enable |
| `gateway call logs --tail`, `config get .` | Both rejected by the 9.2 CLI |
| Codex plugin is bundled in the image; `doctor` refreshes any volume copy itself | The entrypoint's pin-reinstall step cannot run on 9.2 (it refuses on invalid config), and the root-ownership dance it exists for is no longer required |

## Design

Additive and idempotent, in the same style as every other SnapClaw boot step. No new
subsystems. Net effect on the tree is a deletion: the sudo helper, the sudoers rule, the
codex reinstall block and `reownPlugins()` all go.

### Version pin and image

`Dockerfile`: `ARG OPENCLAW_VERSION=2026.9.2`; builder stage `node:24-bookworm` so
`node-pty` is built against the runtime ABI. Remove the global `npm install grammy
@grammyjs/runner @buape/carbon` — the official image now bundles the Telegram plugin with
its dependencies (its own build verifies `import("grammy")`), and a second copy on the
global path is a version conflict waiting to happen. Remove `sudo`, the sudoers rule and
`scripts/own-plugins.sh`. Keep `tini` and `gosu`.

`package.json`: `engines.node >= 24`, version `0.10.0`.

### State migration at boot

New step in `gateway.ts` `startInternal()`, before `ensureConfig()`:

```
migrateState():
  current = `openclaw --version`            (already cached at boot for /api/status)
  marker  = STATE_DIR/openclaw-version      (absent on every existing deploy)
  if marker == current: return
  run `openclaw doctor --fix --non-interactive` (timeout 5 min)
  if exit 0: write marker
  else: log and continue — never block boot
```

`doctor --fix --non-interactive` is what OpenClaw's own Docker docs prescribe for a state
volume that predates the image. Verified on 9.2: exit 0 on a fresh state, on a 5.27 state,
and on a 5.27 state whose plugin tree is root-owned (as SnapClaw's entrypoint leaves it);
idempotent (completed migrations are receipted and not replayed); `--non-interactive`
means "safe migrations only" and that set covers everything the upgrade needs — config
keys, `openai-codex/*` → `openai/*` model refs with `agentRuntime.id: "codex"` preserved,
workspace setup state, device identity, plugin registry, and the stale Codex plugin
refresh (`@openclaw/codex@2026.9.2` lands in `npm/projects/openclaw-codex-*/`, owned by
`node`).

Running it per OpenClaw version rather than per boot keeps the ~10 s cold start off the
normal restart path. The marker lives on the volume next to `setup-password` and
`session.secret`, so it survives redeploys and resets with the volume.

The `openclaw.doctor` action in the admin panel changes to `doctor --fix --non-interactive`
for the same reason: `runCmd` has no TTY, and 9.2's doctor prompts.

The 0.9.x comment forbidding `doctor --fix` on every boot stays true in spirit — it is now
run once per OpenClaw version, and the reason it was banned (a 2026.5.5 doctor rewrote
`openai-codex/*` routes) is precisely the migration 9.2 requires.

### Codex provider rename

`index.ts` `startCodexSession()`: `--auth-choice openai` for first-time onboarding,
`models auth login --provider openai` for re-auth. The PTY flow is unchanged — 9.2's
`models auth login` still requires a TTY, still prints the OAuth URL, and OpenClaw's Docker
docs still describe the paste-the-redirect-URL flow. `--device-code` exists as an
alternative and is deliberately not adopted: it would change the UI for no gain.

### "Codex connected" status

Replace the `auth.profiles` read with `openclaw models auth list --provider openai --json`
and test `profiles.length > 0`. The output is `{ agentId, agentDir, authStatePath,
provider, profiles: [...] }` and never contains token material.

The status endpoint is polled by the panel, and this is a CLI cold start, so the result is
cached for 60 s and invalidated when a Codex session finishes or the gateway restarts.
Drop `auth` from the `OpenclawConfig` type.

### Telegram

`handleTelegramAdd` runs `openclaw channels add --channel telegram --token <token>` instead
of `config set channels.telegram.botToken`. Verified: it writes `channels.telegram.botToken`,
`channels.telegram.enabled: true` and `plugins.entries.telegram.enabled: true`, so
`checkChannelsReady()` keeps reading the same key. The gateway restart that follows is
unchanged.

Remove the `OPENCLAW_TELEGRAM_POLL_STALL_MS` option and its `deepSet`.

### Control UI browser handoff

Device pairing for browsers can no longer be switched off. Instead of putting the operator
through the approval queue, use the handoff OpenClaw added for exactly this case:

```
openclaw dashboard --json --no-open
→ { "browserUrl": "http://127.0.0.1:18789/#bootstrapToken=<single-use>&bootstrapProfile=owner",
    "browserBootstrapExpiresAtMs": ... }
```

The token rides in the URL fragment, which the browser never sends to the server, so the
same fragment works against the public domain. New auth-gated route
`GET /snapclaw/api/dashboard`: mint, then `302 Location: /#<fragment>`. The panel's
"Open Web UI" link points at it. One click per browser profile grants a durable owner
credential; there is nothing to approve.

`gateway.controlUi.allowedOrigins` and `gateway.trustedProxies` stay as they are.
The proxy's `xfwd: true` also stays — the alternative (strip forwarded headers so the
gateway sees a bare loopback peer and auto-approves) is undocumented behaviour, and the
handoff is the documented one.

### Retired config keys

`ensureConfig()` stops writing `gateway.controlUi.allowInsecureAuth`,
`gateway.controlUi.dangerouslyDisableDeviceAuth` and
`channels.telegram.pollingStallThresholdMs`. Doctor removes the existing values from every
deployed config during migration. Nothing replaces them: token auth over the loopback
proxy works without `allowInsecureAuth` in 9.2 (verified — gateway ready, `/healthz` 200
behind the same proxy shape), and device auth is handled by the handoff above.

Everything else `ensureConfig()` writes was checked against the 9.2 schema and is
unchanged: `gateway.mode`, `gateway.auth.mode/token`, `gateway.remote.token`,
`gateway.trustedProxies`, `gateway.controlUi.allowedOrigins`, `tools.profile` (`full` is
still one of `minimal|coding|messaging|full`), `tools.allow/alsoAllow`, `plugins.allow`,
`plugins.entries.bonjour.enabled`, `browser.*`.

### Removed machinery

- `docker-entrypoint.sh`: delete the Codex version-reconcile block and the `chown -R 0:0`
  of the plugin root. Keep the volume `chown -R node:node /data` and the `openclaw.json`
  ownership line. In 9.2 the plugin ownership check accepts a directory owned by the
  running uid, `doctor` performs the refresh, and the legacy root-owned copy under
  `npm/node_modules/@openclaw/codex` is simply left unused.
- `gateway.ts`: delete `reownPlugins()`.
- `openclaw gateway stop` before spawn: in 9.2 this is the *service* stop
  (launchd/systemd) and only prints a warning in a container. Replace with `--force` on
  `gateway run`, which kills whatever holds the port.

### Defaults

- `memory.search.provider = "none"` **only if absent**. SnapClaw users authenticate with
  ChatGPT OAuth, which OpenClaw documents as "chat/completions only" — embeddings need an
  API key. Without this, `memory_search` reports memory unavailable and every doctor run
  warns. `"none"` is the documented FTS-only mode. Set-if-absent rather than forced,
  because an operator who adds an API key later must be able to switch it on.
- `update.checkOnStart = false`, forced on every boot like the other `ensureConfig()` keys.
  SnapClaw pins the version; the anonymous update ping and
  the "update available" log line are noise. (`update.auto.enabled` defaults to `false`,
  so the pin is not at risk either way.)
- Doctor creates a 30-minute heartbeat monitor and a memory-core "dreaming" cron on every
  agent. Both are OpenClaw defaults and both spend model turns on the operator's ChatGPT
  quota. Left as-is; the CHANGELOG documents the switch
  (`agents.defaults.heartbeat.every: "0m"`).

### Minor CLI renames

| Panel action | Was | Now |
| --- | --- | --- |
| `openclaw.logs.tail` | `gateway call logs --tail N` | `openclaw logs --limit N --plain` |
| `openclaw.config.get` | `config get .` | serve `readConfig()` through `redactSecrets` |
| `openclaw.doctor` | `doctor --fix` | `doctor --fix --non-interactive` |

### Operator-facing upgrade notes (CHANGELOG / README)

- Redeploy. The first boot runs OpenClaw's state migration (about a minute on Railway);
  the gateway is up after it, Telegram pairing and the Codex login carry over.
- Export a backup from the panel before redeploying. The migration keeps `.migrated`
  originals on the volume, but the export is the rollback that is actually tested.
- Control UI: click **Open Web UI** in the panel once per browser. Old bookmarks of the
  bare domain will show "pairing required" until then.
- Background model usage is now on by default (heartbeat every 30 min, nightly memory
  consolidation) and how to turn it off.
- `OPENCLAW_TELEGRAM_POLL_STALL_MS` is removed.

## Verification

1. `npm test` — `node --test` (stdlib, no dependencies) over the pure helpers: version
   marker comparison, dashboard fragment rewrite, auth-list parsing. Three assertions.
2. `docker build` locally: `node-pty` compiles on Node 24, `sudo` and grammy are gone from
   the image.
3. Run the built image against a rehearsal volume produced by a real 5.27 onboard
   (the same procedure used to verify this design): first boot logs the migration once and reaches `/healthz` 200
   with the Codex plugin at 2026.9.2; second boot skips the migration.
4. Staging service on Railway with an import of a real production export — the two things
   a synthetic state cannot prove: a genuine Codex OAuth profile migrating into SQLite and
   still answering in Telegram, and the Control UI handoff working through Railway's edge.
5. Only then tag 0.10.0.

## Rollback

Redeploy SnapClaw 0.9.20 and import the pre-upgrade export. A 5.27 gateway will not read
a volume that 9.2 has migrated, so the export is the rollback path, not the `.migrated`
files.

## Out of scope, noted for later

- **`memory-wiki`** is now a bundled plugin ("persistent wiki compiler and Obsidian-friendly
  knowledge vault", `wiki_search/get/apply/lint`, no API key). It implements the pattern the
  vault design was going to hand-roll; the vault spec should be revisited against it.
- Backups: `/api/export` tars the volume while the gateway runs. With SQLite/WAL now
  central to state, it should stop the gateway first or call
  `openclaw backup create --verify`.
- `/healthz` could report `/readyz` (channel-aware) instead of process liveness.
- `automations create --declaration-key` gives idempotent cron jobs without a marker file.
